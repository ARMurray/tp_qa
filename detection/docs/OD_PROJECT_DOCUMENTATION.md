# Wastewater Treatment Plant Object Detection Module — Project Documentation

This document supersedes and consolidates `PROJECT_OVERVIEW.md`, `IMPLEMENTATION_PLAN.md`,
and `CURRENT_STATUS.md`. Those described the project through round-1/early-round-2 local
annotation and training; this version reflects the pipeline as it stands after the HPC
migration, the Parquet output schema, and the mapping/QA tooling built since. Where the
older docs and current reality disagreed, current reality wins.

---

## 1. Background & Goal

This module is a computer-vision component of a larger effort to correct incorrectly
reported geographic coordinates for wastewater treatment plants in the United States.
An existing random-forest model corrects coordinates using text/locational fields alone;
approximately 40% of reported plant coordinates are wrong, and this module adds a signal
based on actually detecting treatment infrastructure in aerial imagery.

**Goal:** train an object detection model that finds specific wastewater treatment
infrastructure in NAIP aerial imagery. Detected bounding box centroids, aggregated and
deduplicated across overlapping tiles, produce a corrected coordinate per facility.

**Where this is headed (see §9):** the intended integration is a three-step
correction workflow — (1) is the reported location likely correct, using detection
signal as one input; (2) if not, narrow candidate parcels within a search radius down
to ~10-20; (3) run targeted, lightweight object detection against only those candidates
to pick the best one. This document is written to be handed to that location-correction
project as the reference for how the detection module works and what it outputs.

## 2. Repository & Environment Structure

Training happens **locally only** (small dataset, GPU-bound, iterative). Large-scale
NAIP extraction and inference across the full ~17,877-plant universe happens **on the
HPC only** (network- and volume-bound, not GPU-bound at this model size). The two
environments have separate, non-interchangeable copies of the pipeline scripts and a
separate `config.py`, sharing only the tile-geometry/CRS contract and the trained model
weights file (copied HPC-ward after each local training round).

### 2.3 Tile geometry & CRS contract (must match exactly, both environments)

| Constant | Value | Notes |
|---|---|---|
| `TILE_SIZE_M` | 200 | tile width/height in meters |
| `OVERLAP_PCT` | 0.33 | fractional overlap between adjacent tiles |
| `STRIDE_M` | ~134 | `TILE_SIZE_M * (1 - OVERLAP_PCT)` |
| `TARGET_RES_M` | 0.6 | standardized resolution regardless of native NAIP resolution (30cm or 60cm by state) |
| `IMAGE_PX` | 333 | `TILE_SIZE_M / TARGET_RES_M`, rounded |
| `MODEL_IMGSZ` | 352 | `IMAGE_PX` rounded up to the nearest multiple of YOLO's stride (32); passed explicitly to `model.train()`/`model.predict()` to avoid Ultralytics silently rounding and warning on every call. Detected box coordinates still come back in the original 333px space. |
| `EXPORT_CRS` | 4326 (WGS84) | NAIP is requested with `imageSR=4326`; all pixel<->lon/lat math assumes this |
| `PROJECTED_CRS` | 5070 (Albers CONUS, meters) | used for tile-grid generation and distance math |

### 2.4 Model weights convention

Exactly **one** `.pt` file is kept in the HPC `models/` folder by convention.
`07_run_state_pipeline_hpc.py` and `05_run_inference.py` both auto-select the most
recently **modified** file in their respective models directory rather than trusting a
pinned run-name-based path — this was a deliberate fix after a bug where a stale
`RUN_NAME` silently kept resolving to an old model indefinitely (see §7). Auto-selection
by mtime is convenient but not foolproof (re-uploading an older file can make it look
newest) — keeping only one file removes the ambiguity entirely. An explicit
`--weights` (HPC) / `EXPLICIT_WEIGHTS` (local) override exists for the deliberate
multi-model comparison case.

## 3. Data Sources

### Treatment Plant Locations
- **Full production universe** (`data/plants.gpkg`, layer `treatment`): built in R,
  ~17,877 plants, columns `CWNS_ID` + point geometry only. Geometry is the
  best-available location per plant (includes manual corrections where they exist).
  This is what the HPC pipeline tiles — **not** the training sample below.
- **Training sample** (`data/training_sample_round2.gpkg`): 190 plants stratified by
  Census region × population bin, **for annotation/training only**. Built from
  `Updates.gdb` → `CWNS_Locations`, using `Corrected_X/Y` where `How_Corrected == "Parcel"`
  and `Original_X/Y` where `Original_Correct == "Yes"`.
- State selection throughout the HPC pipeline uses `CWNS_ID`'s first two characters as
  the Census state FIPS code directly (validated at build time — see §00_build script).

### TRI Facility Locations (hard negatives, training only)
- EPA TRI Feature Service, filtered to `INDUSTRY_CODE IN ('322','324','325','331') AND
  ONSITE_WATER = 0` — industrial confusers (tanks, rectangular structures) with no
  water treatment, used to teach the model not to false-positive on similar-looking
  industrial infrastructure. 50 facilities in the round-2 sample.

### Parcel Boundaries
- Regrid parcel data, parquet, nested `state=XX/{county_GEOID}.parquet`, geometry as
  WKB in `wkb_geometry`, ID field `ll_uuid`. Used for treatment plant tiling only (TRI
  uses a single fixed-radius tile per point, no parcel join).

### Counties
- TIGER/Line county boundaries, built in R (`data/counties.gpkg`), used for GEOID
  lookup to locate the correct parcel parquet file. Deliberately staged as a local
  file on both machines rather than calling `pygris` at runtime, since compute nodes
  may have no outbound internet (confirmed to be a real constraint on this cluster —
  see §6 benchmark history).

### Aerial Imagery
- NAIP (National Agriculture Imagery Program), USDA CONUS PRIME ArcGIS REST
  ImageServer: `https://gis.apfo.usda.gov/arcgis/rest/services/NAIP/USDA_CONUS_PRIME/ImageServer`
- 4 bands (R, G, B, NIR), native resolution 30cm or 60cm by state, standardized to 60cm.
- RGB (bands 1-3) saved as PNG for annotation/inference; NDWI computed from
  Green/NIR and saved as float32 GeoTIFF (currently **unused by the deployed model** —
  training and inference are RGB-only; NDWI remains deferred, see §9).

## 4. Infrastructure Classes

Six classes were originally annotated; **the currently deployed model is trained on a
3-class subset**, filtered at training time without re-annotating anything (see
`04_train_model.py`'s `KEEP_CLASSES`).

| Class | YOLO ID (full 6-class scheme) | Description | Status in deployed model |
|---|---|---|---|
| `aeration_basin` | 0 | Rectangular mixing tanks | **Included** |
| `chlorine_contact` | 1 | Elongated rectangular contact chambers | Excluded (deferred) |
| `clarifier` | 2 | Circular settling tanks, very distinctive | **Included** |
| `digester` | 3 | Covered circular tanks | **Included** |
| `drying_bed` | 4 | Rectangular sludge drying cells | Excluded (deferred) |
| `oxidation_pond` | 5 | Large open-water lagoons | **Excluded — needs a separate model** (see below) |

**Why `oxidation_pond` is excluded, specifically:** lagoons/oxidation ponds are
frequently larger than the current 200m tile can meaningfully contain, which both
degraded detection quality and complicated dedup. The decision was made to build a
**separate future model using larger tiles** for this class rather than force it into
the current geometry (see §9). `chlorine_contact` and `drying_bed` are excluded from
the current deployed round for now; re-including them (or building further rounds) is
a straightforward re-run of `04_train_model.py` with a different `KEEP_CLASSES` list —
no annotation work is lost, since filtering happens on a copy of the dataset, never
on the original Label Studio export.

Class-filtering mechanics: `04_train_model.py` copies `dataset/` into
`dataset_filtered/`, drops label lines for excluded classes, and remaps kept classes
to a clean `0..N-1` range in alphabetical order (matching the original class-map
convention). A tile whose only annotation was an excluded class becomes a legitimate
negative for the kept classes, not a discarded tile.

## 5. Pipeline Stages & Outputs

| Stage | Local script | HPC script | Role |
|---|---|---|---|
| Training-sample construction | `01_sample_sites.py` | — | Stratified 190-plant + 50-TRI sample for annotation |
| Full-universe plant list | — | `00_build_full_plant_list_hpc.py` | Reads `data/plants.gpkg`, validates `CWNS_ID` (catches leading-zero truncation), attaches `st`/`geoid`, writes `all_plants.gpkg` |
| Tile extraction | `02_extract_tiles.py` | *(folded into 07, see below)* | Fetch NAIP tiles for a parcel grid |
| Dataset prep | `03_prepare_dataset.py` | — | Label Studio YOLO export → `dataset/` (plant-level train/val split) |
| Training | `04_train_model.py` | — | YOLOv8s, optional class-subset filtering |
| Inference (small-scale/local) | `05_run_inference.py` | *(folded into 07, see below)* | Runs the trained model on already-extracted tiles |
| **Full-state pipeline** | — | `07_run_state_pipeline_hpc.py` | **Fused**: extract → infer → keep/delete tile → dedup, per state, in one job |
| Map/QA review | `06_build_map.py` | — | Builds a self-contained MapLibre HTML map from downloaded Parquet output |

### 5.1 Why extraction and inference are fused on the HPC

`07_run_state_pipeline_hpc.py` fetches each tile, runs inference **immediately**, and
deletes the tile image on the spot if zero detections come back — keeping peak disk
usage bounded to roughly what's in flight, never a full state's worth. Nothing
spatial is lost when a tile is deleted: its bbox is deterministic (same bbox + the
fixed tile geometry always reproduces the same NAIP fetch) and is logged regardless
of outcome in the `tiles` table (§5.2) — a deleted tile can always be re-fetched
later from its logged bbox.

### 5.2 Parquet output schema (`data/inference_state/{table}/state={fips}/*.parquet`)

Four tables, append-only (every pipeline run/retry adds new part-files; nothing is
ever overwritten), forming a hierarchy joinable top-to-bottom for review:

**`tiles`** — one row per tile *attempted*, regardless of outcome:
`tile_id, CWNS_ID, st, geoid, state_fips, parcel_id, tile_row, tile_col,
bbox_xmin/ymin/xmax/ymax, outcome (kept/deleted/fetch_failed), is_nodata,
n_raw_detections, image_path, fetch_time_s, infer_time_s, fetch_error, tile_size_m,
target_res_m, image_px, model_weights, conf_threshold, iou_threshold, processed_at`

- `is_nodata` is independent of `outcome`: NAIP can return a *successful* fetch that's
  still blank (ocean, coverage gaps, flight-line seams) — flagged via near-zero pixel
  variance, distinct from "genuinely looked and found nothing."

**`detections`** — one row per raw YOLO box, pre-dedup:
`detection_id, tile_id, CWNS_ID, class_id, class_name, confidence,
px_cx/cy/w/h, px_xmin/ymin/xmax/ymax, lon, lat, geo_xmin/ymin/xmax/ymax,
touches_tile_edge, edge_margin_px, model_weights, processed_at`

- `touches_tile_edge`/`edge_margin_px` flag boxes that touch or nearly touch the tile
  boundary — direct signal for the "was this an awkward edge cut" review question.

**`objects`** — one row per merged real-world object (post geographic-NMS):
`object_id, CWNS_ID, st, geoid, state_fips, class_id, class_name, lon, lat,
max_confidence, mean_confidence, n_merged, member_detection_ids (list),
geo_xmin/ymin/xmax/ymax (union bbox across merged detections), model_weights,
processed_at`

**`plants`** — one row per plant's final corrected coordinate:
`CWNS_ID, st, geoid, state_fips, corrected_lon, corrected_lat, selection_strategy,
n_objects, n_detections, dominant_class, class_counts (list of {class_name, count}),
member_object_ids (list), orig_lon, orig_lat, offset_m, model_weights, processed_at`

Geographic NMS (`geographic_nms()`) and the plant-level selection
(`select_plant_coordinate()`) are two explicit stages, not one collapsed step —
this is what lets `objects` be written out as its own reviewable table rather than
disappearing into a single flattened per-plant result.

### 5.3 Map / QA tool (`06_build_map.py`)

Reads every part-file under `--inference-dir/{detections,objects,tiles,plants}` and
aggregates automatically — download more states into the same local folder, rerun,
done. Self-contained HTML (MapLibre GL JS vendored locally, no outbound requests),
dual Esri basemap (streets/imagery, toggle button, no API key). Layers:

- **Facilities** (always on) — reported/best-available location per plant with a
  result, from `data/plants.gpkg`.
- **Detections** (always on) — raw per-box points, colored by class, sized by confidence.
- **Object boxes** (toggle, off by default) — merged post-dedup objects as polygons
  (union bbox), same class colors.
- **Tile boxes** (toggle, off by default — 33% overlap means heavy visual clutter if
  always on) — every attempted tile's exact footprint, colored by outcome
  (green=kept, gray=deleted, red=fetch_failed); click anywhere inside one for its
  `tile_id`/outcome/detection count.
- **Confidence slider** — filters detection points and object boxes together in real
  time (`map.setFilter`); tile boxes are unaffected (no confidence field applies).

Must be served via `python -m http.server`, not opened via `file://` — MapLibre's
background Web Worker is blocked by Chrome/Edge on the `file://` scheme.

## 6. Current Status

- **Model:** the currently deployed model is the 3-class filtered model
  (`aeration_basin`, `clarifier`, `digester`) trained via `04_train_model.py`'s
  `KEEP_CLASSES` filter, superseding the earlier full 6-class round (which had a
  known primary failure mode of `oxidation_pond` false-positiving on natural water —
  moot now that the class is excluded pending its own model). Exactly one `.pt` file
  is kept in the HPC `models/` folder per the convention in §2.4.
- **HPC migration:** complete and validated. Environment set up (`naip_pipeline_env`,
  Python 3.13, CPU-only PyTorch), connectivity/throughput benchmarked
  (`benchmark_naip.py`): ~10-15 tiles/sec achievable with 10 concurrent fetch workers,
  no meaningful gain from more; **CPU inference confirmed sufficient** (NAIP fetch is
  the bottleneck, not YOLO inference at this image size), so the decision was made to
  stick with CPU rather than queue for shared GPU nodes.
- **First full state run:** Ohio (FIPS 39) has been run end-to-end on the current
  3-class model, writing the Parquet schema in §5.2. Output downloaded locally and
  reviewed via `06_build_map.py`.
- **Review of Ohio results surfaced two open issues** — see §7.

## 8. Future Plans

Explicitly planned next steps, in rough priority order:

1. **Increase the deduplication (NMS) distance threshold** — current 12m is too
   tight for large real-world objects like clarifiers; likely needs to be
   meaningfully larger, and/or replaced with an overlap/IoU-based merge criterion
   that scales with object footprint rather than a flat distance.
2. **Experiment with tile overlap distance** — currently 33% (stride ~134m); revisit
   whether this is the right value now that real detection/dedup behavior can be
   observed on a full state's worth of data.
3. **Consider increasing image tile size** — both as a general revisit and
   specifically to support a future model for `oxidation_pond`/lagoon-scale
   infrastructure, which the current 200m tile can't reliably contain.
4. **Build the separate larger-tile lagoon/oxidation-pond model** once tile size is
   settled — a distinct model, not a retrain of the current one.
5. **Confirm the basemap-vs-NAIP alignment question** (§7) by direct tile-vs-box
   comparison, independent of the Esri basemap.
6. **Resolve the two "please verify" filename/import items** in §7 before the next
   HPC run.
7. **Roll out remaining states** via `submit_all_states.sh` once the dedup threshold
   fix is validated on at least one more state.
8. **Revisit annotation policy for edge-cut tiles** — avoid annotating tiles where an
   object is cut awkwardly at the tile boundary; given 33% overlap, a whole-object
   version of the same object should exist in a neighboring tile. An object larger
   than the overlap buffer (never whole in any tile) is itself useful signal, not
   just an annotation nuisance.
9. **NDWI 4-band input** — remains deferred; more labeled data continues to be judged
   more valuable than the extra channel at current data volumes.

## 9. Integration with the Location Correction Workflow

The location correction workflow is a separate project/repo and currently operates
in two steps: (1) determine whether a reported coordinate is likely correct, and (2)
if not, search outward across surrounding parcels for a better one. Pulling NAIP
imagery and running detection across every parcel within a 5-10km search radius would
be prohibitively expensive at full scale, so the proposed integration is a **three-step**
version:

1. **Step 1 (correct vs. incorrect):** fold detection signal in as *one input feature*
   to the existing correctness decision (e.g., distance from the reported point to the
   nearest detected object of a plausible class) rather than a hard override — a
   confident non-detection near an otherwise-plausible point is different evidence
   from no imagery signal existing at all.
2. **Step 2 (candidate narrowing, unchanged in spirit):** the existing outward-search
   logic narrows the candidate parcel set down to a manageable number (~10-20),
   without any imagery pulled yet.
3. **Step 3 (new):** run object detection *only* against those 10-20 candidate
   parcels, using the detection signal to pick the most likely correct parcel.

**Architectural implication for this module:** step 3 needs a lightweight,
single-plant, low-latency version of the tile-and-infer logic — not the full-state
batch pipeline in `07_run_state_pipeline_hpc.py`, which is tuned for wall-clock
efficiency across an entire state's worth of plants, not fast turnaround on one
flagged plant's handful of candidate parcels. This is a new, smaller entry point to
be built when the location-correction side is ready to integrate, reusing the same
tile-geometry/CRS contract (§2.3) and the same trained model, but not the same
orchestration code.
